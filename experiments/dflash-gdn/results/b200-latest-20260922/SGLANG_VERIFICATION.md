# SGLang DFlash verification

- Inspected the installed SGLang 0.5.20 code and recorded 4B/27B server logs. Adaptive speculation and ReplaySSM were disabled; overlap scheduling was enabled for both baseline and DFlash.
- DFlash fixes the block size at initialization, then passes all 16 positions per request to the target before acceptance. There is no confidence truncation or adaptive verification in this execution path: [worker initialization](/home/tomasruizt/code/sglang-bench/.venv/lib/python3.12/site-packages/sglang/srt/speculative/dflash_worker_v2.py:456), [target verification](/home/tomasruizt/code/sglang-bench/.venv/lib/python3.12/site-packages/sglang/srt/speculative/dflash_worker_v2.py:2587).
- Both baseline and DFlash select FlashInfer GDN kernels. DFlash uses the multi-token BF16-state verification kernel, saves intermediate states, then commits the accepted state. This avoids separate target forwards for each accepted token; it does not skip rejected candidates' verification: [GDN verification](/home/tomasruizt/code/sglang-bench/.venv/lib/python3.12/site-packages/sglang/srt/layers/attention/linear/kernels/gdn_flashinfer.py:584).
- At c=32, 27B improves from 3,331.81 to 4,667.50 tok/s (+40.1%), with acceptance length 7.59. 4B decreases from 9,658.22 to 9,546.29 tok/s (-1.2%), with acceptance length 5.53. These are single runs, not a guarantee of improvement.
- The added Qwen3.6-35B-A3B runs improve from 4,121.79 to 6,710.99 tok/s (+62.8%) at c=32, with acceptance length 6.59. Both use Triton MoE after release-default TRTLLM failed at startup. Client concurrency is not a constant verification batch size: the sampled running-request gauge peaks at 31 for MoE DFlash, versus 32 for its baseline.
- Interpretation: 32 requests × 16 positions = 512 verification positions, but this does not establish that the complete step is compute-bound. Larger matrix operations, amortized weight reads/launches, and multi-token GDN execution can compensate for rejected work. DFlash wins when draft + verification + bookkeeping costs less than the baseline steps needed to emit the same accepted tokens.
- Kernel-level profiling is needed to attribute the measured gain or establish the compute/memory bottleneck. The code confirms full-block verification, not the relative contribution of each optimization.
- Current [SGLang documentation](https://docs.sglang.io/docs/advanced_features/speculative_decoding) describes adaptive speculation for EAGLE; the installed release and recorded runtime settings are the evidence for these runs.
